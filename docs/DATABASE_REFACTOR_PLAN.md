# 数据库统一业务状态改造方案

日期：2026-10-15。改造前 Git 基线：`4b6a698`。目标：订单、库存、预留、箱位、执行证据和业务申请均以 SQLite 已提交记录为准，清理旧内存账本和整包状态快照。视觉输出仍来自 RGB-D，不用数据库历史坐标代替识别。

## 选型与边界

- 当前是一台主机、一个物理执行器，沿用 SQLite 即可支持持久化、事务和查询；无需再部署数据库服务。
- 不引入 ORM：使用两个职责明确的 Repository 封装 SQL，避免业务层散落查询，同时便于学习事务、约束和并发。
- 配置、模型、场景资产仍保留在 YAML/文件中；图像和 ROS 运行句柄不塞进业务关系表。
- “状态唯一来源”不代表数据库能保证识别正确或机械臂成功；物理事实仍必须由实际感知与执行验证提供。

## 1. 结构与清理范围

- `database.py`：替换 `persistence.py`；统一连接、嵌套事务、版本迁移、执行记录、申请和事件。
- `inventory_repository.py`：替换 `inventory.py`；数据库中的观测关联、预留、状态转换、时效和冲突规则；不持有 `_items`、`_executing` 常驻账本。
- `resource_repository.py`：替换 `scheduling.py`、`fulfillment.py`；订单、明细、排队、箱位和分配均查询数据库；返回的记录是不可变查询结果。
- `order_server.py`：保留 ROS 接口与实时运行状态；删除快照拼装/对象重建与暂停订单业务缓存；事务完成后才派发 Action。
- `business.py`：MCP 业务操作直接读写同一数据库；改单及审批状态在同一事务提交，取消手工深拷贝回滚。
- `runtime.py`、`execution_bridge.py`：保留当前候选、机器人句柄和物理执行控制；装箱验证、库存消耗与订单明细更新通过数据库记录；不以内存数量作为持久业务账本。

## 2. 数据与约束

- `orders` / `order_lines`：订单、优先级、持久顺位、状态、版本、各 SKU 请求/已验证数量。
- `inventory_items` / `inventory_observations`：内部物品 ID、场景批次、观测位置/时间、有效性与历史；ID 唯一不等同于视觉身份绝对正确。
- `reservations`：物品与订单关系；保留预留、搬运、消耗、释放历史；同一物品只能存在一份有效占用。
- `bins` / `bin_allocations`：箱位定义、当前占用与绑定历史；一个箱位不能同时归属两单。
- `placed_items`：已验证装箱的物品、实体名称、箱位、来源及目标；支撑取货和安全暂停后继续，不保存机器人对象。
- `operations` / `requests` / `events`：沿用并完善已有执行意图、审批和审计证据。
- 外键、CHECK、唯一/部分索引约束业务关系；使用参数绑定 SQL。`PRAGMA user_version` 管理结构版本。

## 3. 事务与实时执行边界

- 接单：订单主体、明细一次提交；相同请求幂等，不同内容同 ID 拒绝。
- 调度：重新校验库存和箱位、完整预留、箱位绑定、待派发状态一次提交。无资源不留下部分占用。
- 取消/改单：订单、预留释放和审批结果一次提交。
- 抓放：执行前提交意图；不持有数据库事务等待模型、视觉或运动。物理验证后短事务提交装箱记录、消费预留、进度和操作结果；结果未知进入核对，不能重放。
- 取货/丢弃：先验证并完成现场清理，再短事务更新库存、分配与订单；现场清理的中断仍须可核对。
- 发布状态只读；不再按心跳更新整包 JSON。局部事务支持 SAVEPOINT，统一由外层提交，禁止内部方法提前提交。

## 4. 迁移与恢复

- 在副本上验证旧数据库迁移；正式迁移前使用 SQLite backup 生成一致备份，不删除用户报告和原始数据。
- 旧 `snapshots` 一次性导入关联表，迁移成功后删除旧表；运行路径没有旧快照兼容后端。
- 旧订单、箱位、验证数量和操作 ID 保留；旧视觉观测不可直接恢复为可抓库存。
- 重启将未完成物理任务和未结束占用隔离；新观测需重新关联，不能因重启/时钟恢复自动继续运动。
- 上一进程的瞬时机器对象不恢复；实体名称等持久记录由当前场景查询重新取得。

## 5. 实施与验收顺序

1. 数据库结构、事务、迁移和不可变查询记录。
2. SQL 库存与资源仓储；移除旧容器模块及全部生产引用。
3. ROS/MCP/BT/运行时接线，清理整包快照和业务状态双写。
4. 数据库定向测试：独立连接竞争、全部回滚、重复操作、断点恢复、迁移、读状态不写盘。
5. 工作站回归、隔离 ROS/MCP/BT、Qt 回归；完整仿真使用单独数据库验证，不把隔离替身测试当作真实运动。
6. 更新运行/学习文档、清理旧接口和测试，最后统一 Git 提交。

## 6. 必须观察到的效果

- SQLite 可直接查询谁在排队、物品由谁预留、箱位属于谁及各件装箱证据。
- 进程重启不丢历史归属和进度，也不继续使用旧视觉坐标。
- 两条独立连接不能同时占用同一物品或箱位。
- 写盘失败后业务操作不出现部分生效；界面不误报成功。
- 原 ROS Action/Service、MCP 工具与界面保持兼容；原有视觉误检与运动局限如实记录。
