# 同一个旧订单的重启续做与百炼连接修复

## 用户要求与旧实现的差别

- 要求：重启后接着完成原八件订单，保留已完成四件，不结束旧单、不重新下单。
- 旧实现：SQLite 保留进度，但只进入 RECOVERY_REQUIRED；未重建仿真实体，不能继续。
- 新实现：在**新启动的 O3DE 仿真**中重建已验证的订单检查点，校验现场，再以原编号进入调度。
- 这不是通用物理机器人断电恢复，也不是任意时刻物理引擎快照；结果未知的机械动作仍须人工核对。

## 模块与数据流

1. `workstation.launch.py` 为完整启动生成仿真实例 UUID 和启动时间，传给子进程。
2. `OrderActionServer._restore_simulation_checkpoint()` 只在重启隔离状态且配置启用时进入，要求仿真时钟处于启动窗口。
3. `simulation_restore.build_restore_plan()` 读取 SQLite 的订单、进度、箱位、装箱、库存代次与物理操作证据，先校验再生成计划。
4. 已确认取走的商品不会作为可用库存重新出现；同代次已装箱商品从源库存里扣除。仍绑定旧单的箱子和已装商品单独恢复。
5. O3DE 生成实体并等待物理稳定，再检查每件已装商品实际在箱内、已离开原来源位置，并同步 MoveIt 的桌面和箱子几何。
6. 事务提交：原进度不变；未完成单变为 PAUSED 且允许调度，已完成单变为 WAITING_PICKUP；箱位不释放。
7. 旧的未消耗视觉候选退役、未消耗预留解除；**不把生成位置写成 AVAILABLE 库存**。剩余商品必须重新视觉识别并经过资源预留。
8. 原订单由现有调度器重新发送，Agent 根据剩余数量规划行为树；原先已完成的四件不进入新计划。
9. 现有行为树、运动 Action、MoveIt 与实际抓放校验继续工作，不使用脚本替代 Agent。

## SQLite 保存什么

- 原订单、四件已装记录、物理操作结果仍使用既有关系表，没有复制出第二套订单/库存账本。
- `metadata.simulation_source_manifest` 保存**仿真生成清单**及库存代次。新建场景或明确补货时更新，用于复原该代次的源实体；不是视觉库存清单。
- 本次旧数据没有清单时，配置显式允许使用旧场景模板重建安全检查点；若模板身份、库存代次或证据无法对上，则拒绝。
- `operations.phase=SIMULATION_RESTORE` 单独记录恢复生成动作，不能算作新的 PICK_AND_PLACE，也不能增加已装箱数量。
- 原单编号：`database-live-20261020-212833-133476`。本次未通过 SubmitOrder 创建新编号。

## 安全边界

- 存在 INTENT/UNCERTAIN 的抓取或结果未知的维护时，禁止自动重建并重试动作。
- 进度必须逐类别与装箱证据一致；没有 VERIFIED 抓放证据的计数不能变成恢复商品。
- 商品身份、箱位目标、有限数值、源库存代次必须一致，箱外目标被拒绝。
- 已有运行实体、同一仿真实例重复恢复均被拒绝，避免重生两份。
- 恢复一半失败时保留原进度及隔离状态。新的完整仿真实例可以将旧的**仅生成实体**的恢复意图标成 SUPERSEDED，保留失败原因；不会这样处理未知抓取。
- 当前障碍物保持禁用，桌面与箱体碰撞检查没有关闭。

## 真实验证中发现并修复的问题

### 1. 首次落箱恢复失败

- 首次把保存的目标直接标成 `panda_link0` 用于生成，恢复商品未实际落在箱内，被校验拦截。
- 原 O3DE 适配器的实体生成使用场景模板 `odom` 约定，不能把 MoveIt 的虚拟参考系名称直接替代。
- 修复为当前固定工作台的 `odom` 生成适配，保留实际落箱与高度检查。
- 第一次失败的恢复操作保留为 SUPERSEDED，未删除或伪造为成功；原四条装箱记录未变。

### 2. 恢复后视觉库存不足

- A1 订单箱遮住剩余苹果；玉米误候选落在胡萝卜处，触发跨类别冲突。
- 恢复场景支持少量指定身份重排，仅在目的位置空闲时使用，并检查工作区、基座距离、商品间距和箱位距离；数量和身份不变。
- 增加可配置的玉米 SAM 掩膜颜色核验：使用当前图像的绿色外皮/黄色籽粒证据，拒绝明显橙色胡萝卜候选。没有使用实体名称或初始坐标做分类。
- 这是当前仿真资产的颜色规则，不宣称能泛化到所有真实玉米、胡萝卜或光照条件。

### 3. Key 正常但常驻 Agent 显示 Connection error

- 同一份 Key 查询模型列表、聊天、强制工具调用均成功，工具调用实际返回 `probe_status` 和 `{"status":"ok"}`。
- 对照测试：`trust_env=False` 直连百炼失败，底层原因为 `[Errno -3] Temporary failure in name resolution`；显式使用桌面 Clash 代理时，同模型聊天成功。
- 终端有 `HTTP_PROXY/HTTPS_PROXY`，后台 systemd 服务没有继承；所以终端测试成功不能证明后台网络通路相同。
- `agent.proxy_url: http://127.0.0.1:7897` 显式配置模型客户端的 HTTP 代理；可用 `PRODUCE_AGENT_PROXY_URL` 覆盖。Key 文件和模型没有更换。
- 仅 `create_model()` 创建的远程模型 HTTP 客户端使用该代理；本地 MCP 的独立客户端仍 `trust_env=False` 直连，ROS DDS 不经该 HTTP 代理。
- 新错误说明保留异常类型链并区分 DNS/HTTP 状态码，不输出 Key、请求头或服务端私密正文。
- Clash 关闭或端口变化时需调整该配置；若改为直连，必须先确保直连 DNS 和网络可用。

## 已执行的验证

- 隔离 SQLite/假仿真测试：旧编号与进度保留、已取货扣除、完成单只待取货、未确认动作/维护阻止恢复、非法目标/错误代次阻止恢复、重复实例拒绝、失败生成隔离、旧生成意图与未知抓取严格区分、恢复摆位不重叠。
- 颜色测试：绿/黄玉米通过，橙色胡萝卜、红番茄和无有效颜色候选被拒绝；原苹果/番茄用例回归。
- 网络测试：连接与超时不误报 Key 无效，HTTP 状态单独报告，不泄漏私密错误正文，模型代理显式且不继承不确定环境。
- 实际使用既有 Key 和同一模型完成代理/直连对照；没有替换模型或伪造响应。
- 真实仿真已恢复同一旧单，从 4/8 继续执行至 **8/8，WAITING_PICKUP**；玉米、胡萝卜、苹果、番茄各 2 件。没有新建订单，也没有自动确认取货，A1 仍绑定原单。
- 最终 SQLite 核对：8 条 VERIFIED 抓放操作、8 条装箱记录、8 条 CONSUMED 预留；与恢复前备份逐字段对照，原 4 条装箱记录的身份、操作编号、来源、目标和确认时间全部保留。
- 原有 4 条 NO_EFFECT 操作仍保留；未消耗的历史预留已解除，不计作库存消耗。数据库 `integrity_check=ok`，`foreign_key_check` 无错误。
- 中途明确补货已把生成清单更新为代次 3、16 件 `_refill_3` 源实体；最后一次重启按该已保存清单恢复，并非程序自行补货。最初旧检查点恢复的剩余源库存为 8 件，两次场景代次不能混为一谈。
- 最终相关回归测试：**218 passed，2 条第三方弃用警告**，耗时 37.44 秒；这是隔离测试结果，不能替代上述真实仿真证据。
