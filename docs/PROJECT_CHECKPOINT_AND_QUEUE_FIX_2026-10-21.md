# 项目阶段评估、操作入口审计与队列修复

## 1. 结论

- 建议冻结新增大功能，进入源码学习、文档整理和开发版发布阶段。
- 当前已经不是只演示一次抓放的原始 demo：有订单、资源预留、多订单调度、Agent/MCP、受约束计划到行为树、运动规划、SQLite 和恢复边界。
- 适合定位为“基于 RobotecAI RAI demo 二次开发的 ROS 2 + Agent 生鲜配货仿真工作站”。不应描述成从零开发、工业稳定系统或端到端 VLA。
- ROS 2 与 Agent 的项目知识覆盖已经足够；这不等于两个领域的所有技术都已掌握。下一步重点应是能够解释和独立修改现有代码，而不是继续增加技术名词。

## 2. 压力测试中哪些操作没有经过界面

统计范围：`central-native-20261021.jsonl`，不是所有历史排障操作的总和。

| 操作 | 后台入口 | 成功次数 | 界面对应入口 |
|---|---|---:|---|
| 登记订单 | `/produce_orders/submit` | 16 | 提交订单 |
| 补货 | `/produce_orders/replenish` | 9 | 补货准备 |
| 视觉复查 | `/produce_orders/refresh_inventory` | 11 | 视觉复查 |
| 确认取货 | `/produce_orders/confirm_pickup` | 12 | 确认取货 |
| 合计 | 四类业务操作 | 48 | 本批脚本没有通过鼠标点击执行 |

- 另有 34 次确认取货返回“忙”，包含重试在内共 82 次服务调用尝试，不是 82 次成功业务操作。
- 脚本订阅状态话题、只读查询 SQLite，核对订单进度、消耗预留、装箱和 VERIFIED 操作数量。没有直接修改生产数据库来完成订单。
- 此前排障还通过 ROS 业务接口创建/批准现场重建请求、取消未执行旧单；通过命令行重启进程、编译和启动 GDB。它们不计入上述固定批次的 48 次。
- 界面与脚本使用同一后端业务接口，但脚本不经过 Qt 按钮、选择框、确认对话框和信号响应。因此后端压力测试不能证明界面端到端可用；本次另外执行了界面回归。
- 进程重启、原生调试、编译不需要都变成业务界面按钮。

## 3. 本批真实结果与边界

- 日志记录前三轮完成：12 单、59 件，四箱齐全后统一取货。
- 第四轮完成两单，共 10 件；第三单在 0/5 时因 `No selectable corn candidate` 失败。控制器于 21:00:28 保存 BLOCKED 并退出，没有进入第五轮。
- 因此固定批次在控制器退出前累计完成 69 件，不能宣称五轮通过。
- 随后读取 SQLite 时为 15 单 COLLECTED、1 单 FAILED，累计 77 件。后续变化不属于控制器已核验通过的完整轮次，不能拿数据库最终数量倒推本批五轮通过。
- 测试控制器退出与工作站停止调度是两件事：已经登记的其他订单仍可能继续被工作站调度；脚本不会自动撤销这些业务订单。当前操作记录也不足以可靠归因后续每次操作究竟来自界面还是其他客户端。
- 本批启用了 GDB。调试条件下没有复现此前的原生堆内存错误，不等于普通启动的崩溃根因已修复。
- 按用户要求不再启动新批次，不继续无限排障重测。

## 4. 队列修复

### 原问题

- 主队列包含历史已取货和已失败订单，与单独的历史记录区域重复，旧测试单干扰当前工作。
- 界面只按优先级排序，同级依赖状态消息中的原始顺序，没有显式使用 SQLite 的登记序号。
- 刷新表格时，如果选中订单消失，原行号可能指向另一单，容易让取消操作选错目标。

### 新规则

1. 正在执行/派发的任务置顶。
2. 可参与调度的等待订单按优先级降序、登记序号升序排列；不按订单号字典序排序。
3. 人工核对及保留资源的异常任务单独排在等待区后面；待取货任务再后面。
4. 普通已取货、已失败、已取消记录不再挤入当前队列，仍保留在历史与数据库中。
5. 失败但仍占箱、需要核对的订单不能隐藏，防止丢失现场处理入口。
6. “顺位”改为“等待顺位”，提示它不是无条件执行承诺：缺库存/箱位可跳过；不能打断正在搬运的物品。
7. 按订单 ID 恢复选中项；原订单消失就清除选中，不自动选择另一个订单。

### 对应代码

- `ResourceRepository.snapshot_orders()` 增加已有 `OrderRecord.sequence` 的输出，没有新增数据库表或改变调度算法。
- `OperatorPanel._render_queue()` 完成过滤、显式 FIFO 排序、顺位和选择保护。
- 兼容尚未重启的旧服务：若消息没有 sequence，沿用服务端原有登记顺序。
- 只重新启动界面，不为队列显示修复重启机械臂或仿真。

### 针对性验证

- Qt 界面回归 46 项通过；调度回归 40 项通过，共 86 项。
- 新增覆盖：消息乱序仍按登记序号 FIFO；紧急单优先；历史不混入主队列；占箱失败单保留；选中订单消失不误选其他单；服务端输出持久化登记序号。
- 初次把两组测试放到系统 Python 一起收集时，调度测试缺少 Conda 中的 RAI 依赖，收集失败；随后界面用系统 Python、调度用既有 rai-jazzy 环境分别执行成功。这不是一次真实仿真订单测试。

## 5. 建议增加或调整的按键（本次不额外实施）

| 建议 | 解决的问题 | 约束 |
|---|---|---|
| 暂停调度 / 继续调度 | 操作员希望停止继续执行，但保留队列、箱子和进度 | 当前物品安全放好并退出后暂停，不是急停；不盲目重复动作 |
| 复查并续做选中暂停单 | 当前全局“视觉复查”会间接恢复任务，用户不清楚恢复哪单 | 明确目标与影响；依然重新校验库存和物理状态，不绕过执行门禁 |
| 批量确认已完成订单取货 | 四箱需要逐个选择，复查期间还有忙等待 | 只处理真正 WAITING_PICKUP 的选中订单；逐项显示结果，失败不释放箱位 |
| 导出订单 / 诊断包 | 排障和源码学习需要集中查看日志、计划、事件和数据库证据 | 只读、一致性导出、脱敏，不包含 API Key 或认证令牌 |

- 已有提交、取消、清除等待队列、复查、补货、确认取货、恢复工作台、业务请求审批和清空显示日志，不应重复再添加同义按钮。
- 恢复/重建入口应使用现有审批链和清楚的确认提示，不应添加无条件“失败重试”。
- 这些是下一版的少量操作体验建议，不代表现在继续扩展模块或立即实施。

## 6. 技术覆盖与不应夸大的部分

| 领域 | 当前已经能够沿源码学习的内容 | 仍需明确的边界 |
|---|---|---|
| ROS 2 通信 | 自定义 msg/srv/action、节点间调用、反馈、取消、超时、执行器与回调 | 后端接口测试不等于 GUI 测试；本机通信不等于安全的跨机部署 |
| 感知与运动 | RGB-D、分割、深度与 TF、MoveIt 规划/执行、局部 Cartesian、规划场景 | 漏检、遮挡、源目标过滤仍影响完成率；不等于真机感知抓取验收 |
| Agent | 常驻独立进程、结构化工具调用、上下文、计划校验、候选选择、业务查询 | 模型主要选择 SKU 执行顺序、重试预算及视觉候选，不自由控制关节或修改订单数量 |
| MCP | 客户端/服务端、工具、只读资源、HTTP 与本地权限边界 | 不等于 MCP 的资源订阅、Prompts 等所有能力都已实现 |
| 行为树 | 受约束计划编译成 BT XML、C++ 执行、异步 ROS 步骤、有限重试 | XML 由代码编译，不是模型任意生成并直接执行；运动轨迹仍由 MoveIt 规划 |
| 数据库与工程 | Repository、SQLite 事务、约束、WAL、幂等、意图/结果、异常隔离、恢复 | 数据库中的完成状态必须有物理验证证据；历史坐标不能直接变成可用库存 |

- 不需要为了技术覆盖再硬加 Nav2、Lifecycle、SROS2、多机械臂等与当前单工位目标不直接相关的模块。
- 更有价值的是理解 QoS 为什么这样配、Action 为什么要取消排空、失败为什么不能直接重试、事务为什么不能跨长时间运动等设计理由。

## 8. 建议的源码学习顺序

1. **业务资源链**：OrderActionServer → ResourceRepository / InventoryRepository → 数据库。先理解登记、预留、装箱提交与箱位释放。
2. **Agent 计划链**：AgentDispatcher → ProduceAgentService → ProduceAgent → fulfillment_plan 的上下文、摘要校验和 BT 编译。
3. **执行链**：C++ fulfillment_tree → ExecutionBridge → Workstation → ExecuteMotion → RaiManipulationInterfaceNode / ArmController → MoveIt。
4. **感知链**：MCP get_object_positions → 检测/分割/深度/TF → 候选过滤 → Agent 选择 → 运动前重新校验。
5. **异常与恢复链**：超时/取消、operation 的 INTENT/VERIFIED/UNCERTAIN、review_required、暂停续作及仿真检查点。
6. **展示链**：RosWorker 的线程与服务请求 → OperatorPanel 的状态投影。理解为什么界面不是业务真相来源。

每条链都整理：所属对象、上游输入、下游输出、通信接口、数据库变化、失败出口。用一份成功订单和一份暂停订单对应日志走源码，比继续增加功能更能形成自己的项目能力。
