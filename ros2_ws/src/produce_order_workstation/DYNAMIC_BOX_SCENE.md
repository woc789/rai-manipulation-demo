# 场景修正：按订单放箱、整箱取走、现实周转箱障碍物

日期：2026-10-08；基线提交：`0e26bf3`。这是第 1 步的场景修正，不是新增多订单队列。

## 业务修正

上一版只有“箱子归属”变化，物理场景仍先放四个空箱，取货也只删商品。
新默认配货模式改为：

```text
启动：桌面混合库存 + 一个侧放的待回收周转箱；没有订单收货箱
接单：分配空箱位 → 放入该订单的空箱 → 同步 MoveIt → 开始视觉抓放
配货完成：订单箱和商品留在现场，等待操作员确认
确认取货：删除这份订单商品 → 移走它的箱子 → 同步 MoveIt → 释放箱位
```

A1–A4 现在是四个可用位置，不是四个初始箱子。若有两份未取走的完成订单，
现场会有两只订单箱；不会因新订单凭空清理上一单。
放入空箱、取走整箱是对人工物流的仿真模拟，并未增加搬箱机器人或输送带。
旧分类模式仍使用四个固定箱，默认配货模式不使用这一行为。

## 模块输入输出

- `order_server.execute_callback`：接收箱位分配，将订单和 bin_indices 传给
  `Workstation.ensure_order_bins`。只有空箱生成、实体位置验证和规划场景同步成功，才进入 Agent 抓放。
- `runtime.prepare_scene`：读取完整 YAML；保留收货箱条目为 `_bin_templates`，
  配货模式实际只生成 16 件库存和障碍物。
- `runtime.synchronize_scene`：读取当前存在的订单箱、障碍物实际 TF 姿态；输出 MoveIt 已确认的碰撞物 ID。
- `planning_scene.build_collision_objects`：配货模式允许配置箱位的子集或空集，
  绝不为尚不存在的箱子添加“隐形墙”。原分类模式仍要求完整箱位。
- `runtime.collect_order`：先校验订单商品，再定向删除商品与该订单箱。
  `remove_order_bins` 删除箱子后同步移除其 MoveIt 对象；成功后原取货服务才释放业务归属。
- 动作前失败：清理未用的订单箱；清理/同步失败则保持恢复状态，不误报 READY。
- 面板：初始箱位显示“空位（无箱）”，取货按钮说明“取走整箱”，避免视觉与业务概念混淆。

## 障碍物选择与几何

使用现有可运行的 `toy_box` 木箱模型，命名 `packing_return_crate`，表示工作台边缘
暂存的待回收空周转箱。它侧放、开口朝相机一侧，与接单后开口向上的收货箱区分。
不再用九块黄色方块假扮设备，也没有下载一个未接入仿真资产管线的新模型。

配置姿态：位置约 `(0.43, 0.0, 0.11)`，绕 Y 轴旋转 90°，原模型侧放后高度约 20 cm。
曾尝试 x=0.60 的边缘位置，实际箱子掉落，初始化位姿校验安全拒绝；随后移入桌面稳定区域。
库存按箱子两侧重新摆放，仍是每类 4 件、启动时一次性出现，未改为逐件生成。
实际尺寸和五块碰撞体直接取自 `Project/Prefabs/toy_box.prefab`。
`crate_collision_object` 验证实体位置和朝向，将原局部坐标中的箱底、四面箱壁变换
到机器人基坐标系，分别取保守 AABB 并增加 5 mm 余量。
没有把空心箱子整个填成一个实体方块，避免与真实物理箱体明显不符。

选择边缘位置是为了减少对桌面库存的遮挡，不是承诺每份订单的每条路径都绕行。
规划诊断与真实订单执行是不同证据；若某条轨迹本来不经过箱子附近，没有绕行是正常现象。
不能把“模型已加入 PlanningScene”直接当作“这次订单实际产生了避让”。

## 验证与操作注意

- 自动测试：启动不生成订单箱、接单仅生成所分配箱子、已有箱不能当空箱复用、
  取货定向删除箱子、只同步实际存在的箱子、木箱几何与 prefab 一致、位姿偏移失败关闭。
- 保留前一版箱位业务、视觉安全、运动 Action 和旧方块几何回归测试。
- 没有自行构建或提交仿真订单；操作员填写订单进行真实抓放验收。
- 初始画面中的侧放木箱是待回收障碍物，不是提前生成的订单箱。
- 四个收货箱条目仍在 YAML 中作为生成模板；条目存在不等于启动时生成。
- 实体与箱位记录仍在内存，重启不是业务恢复。本次等待旧订单确认取货后才暂停并重启场景。
